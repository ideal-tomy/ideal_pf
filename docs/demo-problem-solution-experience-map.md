用途：トップの紹介文と、課題解決を説明する詳細ページを制作するための企画資料。

## この表の位置づけ

各デモに一つの中心課題を置き、「誰が困っているか」「なぜデジタル化だけでは解決しにくいか」「業務をどう変えるか」「デモのどこで確かめるか」を対応づけた。

根拠は [紹介データ](../src/data.js)、[内部改善管理](demo-improvements.md)、[紹介文の調査レポート](demo-copy-review-2026-09-12.md)。課題と解決の考え方は、既存の想定利用場面を具体化した編集上の仮説であり、実際の企業へのヒアリングや効果測定の結果ではない。外部デモの再操作は今回行っていない。

タイトルは掲載候補。解決欄は業務改善の方向性であり、記載した効果や仕組みのすべてが現在のデモで実装済みという意味ではない。体験欄は現行紹介データから組み立てた代表的な案内順で、画面間をそのまま連続操作できるかは原稿確定前に確認する。

**体験の区分**

- **操作**：現行データに入力・選択等の操作説明がある。サンプル・固定回答を含む。全機能の動作確認済みという意味ではない。
- **閲覧**：画面や説明を見ることを中心に案内する。保存や提出までできるとは案内しない。
- **準備中**：公開URLなし。体験欄は今後案内したいシナリオであり、現在は紹介ページで概要を伝える。

現行のリンク設定は21件、公開準備中は7件。各行の番号は紹介データの並び順と対応する。読みやすさのため業種別に分けた。

## 4. 担当者と経営者へ伝える内容の使い分け

担当者向けには表の「中心となる課題」を使い、実際の作業を思い浮かべられる説明にする。経営者・管理者向けには、解決の考え方が業務全体のどこに関係するかを補う。

| 改善のテーマ | 関連するデモの番号 | 経営者・管理者に補足する観点 |
|---|---|---|
| 記録・転記・文章作成 | 01・05・12・14・17・27 | 人が確認すべき箇所と、繰り返し作業を見直せる箇所を分ける |
| 情報と対応状況の把握 | 04・10・15・16・23・24・25・28 | 誰が、どこまで対応したかを確認するために必要な情報を整理する |
| 判断材料・比較基準の共有 | 06・09・11・19・20・26 | 担当者の判断を説明・引き継ぎしやすくするための材料をそろえる |
| 知識・経験の活用 | 02・07・08・13・18・22 | 詳しい人の知識を、必要な場面で参照する方法を考える |
| 調整・やり取りの整理 | 03・21 | 最初の依頼や希望入力から、変更・完了までの流れを見渡す |

これらは訴求する観点であり、導入効果の実績ではない。「残業を半減」「売上向上」「ミスを防止」等の成果は、検証や実績が得られてから具体化する。

## 5. 詳細ページの原稿へ展開する方法

1. **冒頭**：タイトル候補＋対象業種・読者＋中心課題を短く示す。
2. **課題の説明**：その仕事で起きる具体的な場面を2〜3例に展開する。業界全体の事実として断定せず、「こうしたお困りごとはありませんか」と問いかける。
3. **改善が進みにくい理由**：表の仮説を、デモ本体の内容と利用者への確認で具体化する。
4. **解決の流れ**：改善前と改善後の作業を対比し、人が判断・確認する場所も示す。
5. **体験への案内**：代表体験の順序と見るポイントを明記する。操作できるものは「デモを試す」、閲覧中心は「デモを見る」、準備中は概要紹介として案内する。
6. **説明資料・動画**：この課題・解決・代表体験と同じ順序で制作する。素材ができた時点で追加し、存在しないPDFや動画のリンクは置かない。

最初の詳細ページ原稿は01の現場写真を候補とする。この表の中心課題を軸に、写真の整理から下書きまでが実際にどうつながるかを確認したうえで作成する。本書では原稿の全面作成、掲載データの編集、デモの改修、PDF・動画制作、公開操作は行っていない。
