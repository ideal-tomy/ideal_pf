# トップ掲載5デモ：App Store風紹介ページへの展開計画

作成日：2026-09-13

> 全28詳細ページへの展開は [全詳細ページ展開PLAN](all-detail-pages-rollout-plan.md) を正本とします。本書は5件限定の先行計画です。削除済みの冒頭補足・スワイプ案内・ギャラリー番号を復活させない方針も、新PLANを優先します。

## 目標と今回の範囲

スマートフォンで開いた瞬間に「何ができるか」「どんな画面か」「どこから試せるか」が伝わる紹介ページへ統一する。建設で採用した短い概要・実画面プレビュー・比較・詳細開閉を基準とする。

今回の実装は建設の画像表示調整まで。残り4件と共通テンプレート化は、この計画に沿って次回実装する。対象はトップ掲載5件の紹介ページであり、トップの大カードはタイトル・要約・色・画像の整合を確認する。デモ本体の機能改修は個別課題として扱う。

## 画像とカードの共通仕様

- 元画像の390×844という撮影サイズを、掲載時に全部見せる前提から外す。
- 表示窓は390×600相当（aspect-ratio: 390 / 600）。横幅に応じて縮小し、画像高さは最大400 CSS px。見出し込みのカードは通常表示でおおむね600px以内を目安とする。
- object-fit: coverで縦横比を保ち、上端を基準に下部を切り取る。実画像ファイルは保持する。高さ600pxに引き伸ばさない。
- スマートフォンはカード幅80%とし、次のカードが少し見える横スクロール。PCは3枚並列を基本とする。中間幅ではカードの可読性を保って横スクロールを許容する。
- 見出しは原則2行、補足は1〜2行。カード内の上部余白と画像開始位置を3枚で揃える。
- 切り取り位置は画面ごとに確認する。結果や要確認表示が下部にある場合、焦点位置をデータで調整するか、その結果が上部に来る状態で撮り直す。
- 文字を小さくして画面全体を押し込まない。画面の大きさと、特徴が見えることを優先する。
- 拡大表示や画像内スクロールは初期実装に追加しない。詳細な操作は実デモへ誘導する。
- 文字拡大時は600px目安より内容の可読性を優先し、見出しや説明を切り落とさない。

## 共通のページ構成

| 順序 | ブロック | 常時見せる内容 | 詳細として開く内容 |
|---|---|---|---|
| 1 | 冒頭 | アイコン、短いタイトル、2行の概要、主CTA、体験条件の要約 | なし |
| 2 | 基本情報 | 対象者・体験範囲・確認の前提など3項目 | なし |
| 3 | 実画面3枚 | 画面ごとの価値を示す短い見出し＋画像 | なし |
| 4 | 業務の変化 | 現在の作業→試せる改善を3組 | 対象業務や課題の背景 |
| 5 | 見どころと手順 | 3項目の見出し | 価値の説明、見るポイント、操作方法、途中からの入口 |
| 6 | 体験条件 | サンプル・実AIの区別、保存や送信など判断に必要な制約 | 詳細条件、利用時の注意 |
| 7 | 終わりと関連 | 自社に置き換える短い問い、冒頭と同じ主CTA、関連デモ | 検討の補足 |

建設の「人が確認」「サンプルはAPIキー不要」を他デモへそのままコピーしない。各デモの事実に合わせてラベルと条件を変える。星評価・所要時間・導入実績・削減率など、根拠のない数値は追加しない。

## 5件の編集方針

以下は src/data.js の掲載情報に基づく計画。デモ本体の現在の挙動は、各ページの実装前に再確認する。

| 対象 / ID | 冒頭の訴求案 | 3画面で見せる内容 | 残す説明・条件と確認事項 |
|---|---|---|---|
| 建設 / construction-record | 現場写真から、報告書まで。 | 写真の分類・命名 → 下書きの確認・修正 → 管理側の確認 | 現行原稿を基準とする。サンプル、実送信なし、人による確認、実写真のAPI送信条件を保持。今回の短い画像表示を基準に共通化する。 |
| 問い合わせ / customer-support | よくある質問に、根拠のある案内を。 | 業種を選ぶ → 質問する → 案内と根拠を見る | 固定回答と実AI接続の違いを冒頭で短く表示。回答結果と根拠が画像の表示範囲に入るか確認。業種カードのキーボード操作は既存課題として扱う。 |
| シフト / shift | 希望を集めて、シフト案へ。 | 希望入力 → 割当案の確認 → 確定・欠勤時の対応 | ルールによる割当であることを保持。現在の3枚目は「確定する」なので、欠勤対応も訴求するなら別途画面を確認し、補足または差し替えを判断。通知の実送信有無を確認する。 |
| 品質 / quality-incident | 品質トラブルの対応を、画面で追う。 | 発見の記録 → 原因候補 → 是正・承認の流れ | 架空データ、原因は候補であること、動かない保存・提出を明示。ナビ名と画面対応のずれを再確認。主CTAは「対応の流れを見る」など、現状の体験範囲に合わせる。 |
| 介護 / kaigo-handoff | 申し送りから、日々の記録まで。 | 申し送りメモ → 面談の確認 → 日報を見る | 3枚を必ずしも一続きの処理と表現せず、記録の種類として案内。録音・固定入力・保存期限・架空データの条件を確認。要確認→提出→一覧の連携は実動作を確かめてから訴求する。 |

配色は既存の各デモカードに合わせる。建設の暖色をすべてに転用せず、問い合わせは紫系、シフト・介護は既存のピンク系、品質は既存の紫・青系を起点に、文字と背景のコントラストを確認する。

## 実装の進め方

1. **建設を基準として表示仕様を確定**
   - 今回の390×600相当の切り取りと最大400pxの画像表示を確認。
   - 320・390・430・700・768・1280pxで画像、見出し、カードの高さを確認する。
   - 画像の重要な部分が残ることと、次のセクションへ進みやすい密度を確認する。
2. **共通の描画とデータ構造を用意**
   - `src/demo-story.js`（新規案）に共通描画を分離し、建設専用CSS名を共通クラスへ段階的に置き換える。
   - `src/demo-stories.js`（新規案）にID別の短い概要・基本情報・3枚のプレビュー・比較・詳細・条件を持たせる。
   - プレビューには画像パス、代替テキスト、短い見出し、補足、切り取り位置を保持する。
   - `src/main.js`は対象IDに共通テンプレートを適用。残る紹介ページの既存表示は維持する。
   - `constructionStory`の原稿と資料書き出しは互換性を維持し、長文原稿を失わない。公開URL・掲載順・状態の正本は既存の`data.js`を使う。
3. **問い合わせで2例目を作る**
   - 建設と異なる業種・色・体験条件で共通化の妥当性を確認。
   - 実画面3枚を見て切り取り位置を決め、回答と根拠が見える状態を優先する。
4. **シフトへ展開**
   - 長い手順説明を整理。確定と急な欠勤対応の位置付けを明確にする。
   - 主CTAと途中から試すリンクが、実際に開始できる画面へつながるか確認。
5. **品質・介護へ展開**
   - 先に上表の未確認事項を確認し、使える範囲に合わせて原稿を仕上げる。
   - 未実装機能を魅力的な見出しで実装済みに見せない。制約は体験判断に必要な位置へ置く。
6. **トップと5ページを通して確認**
   - トップのタイトル・要約・画像と、開いた紹介の内容を揃える。
   - 一覧へ戻る、関連ページへの移動、URL直アクセス、ブラウザの戻る・進む、フォーカス移動と背景操作の抑制を確認。
   - 比較画像と検証記録を保存。公開はローカル実装・確認の完了後に扱う。

## 完了条件

- トップ掲載5件が共通の情報順序で表示され、業種別の内容と色を持つ。
- 一般的なスマートフォン表示で冒頭のCTAと実画面への入口が見える。
- プレビューの画像は上限400 CSS px。標準文字サイズでは見出しを含むカードがおおむね600px以内に収まる。
- 横スクロールはギャラリー内で完結し、ページ自体は横にはみ出さない。
- 画像は変形せず、価値の根拠になる箇所が見える。文章と表示状態が一致する。
- モバイル・PCで各詳細の開閉、キーボード操作、リンクと戻り操作が動く。
- 既存の掲載情報を対応表で照合し、必要な体験条件が欠落していない。
- ビルド成功、ブラウザエラーなし。実機Safariで未確認の項目は記録する。
