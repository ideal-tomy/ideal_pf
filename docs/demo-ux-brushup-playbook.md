**目的:** 指定したデモを、カスタマーサポートで確立した進め方で **1本ずつ** 磨き、決裁者が3分で価値を掴める状態にする

## 1. 使い方（人間側）

チャットでは次のように指定する。**1メッセージで1デモ・1フェーズ** が基本。

```text
対象: <demo ID または リポジトリ名>
Phase UX-0 の計画だけ作って
```

計画を確認したあと:

```text
Phase UX-1 をお願いします
```

以降、受け入れを満たしてから次フェーズを指定する。  
「全部やって」は使わない。探索と実装が混ざり、戻しが大きくなる。

指定できる ID の例: `construction-record` / `shift` / `kaigo-handoff`

---

## 2. 使い方（エージェント側）

ユーザーがデモを指定したら、実装の前に必ずこの手順書を読む。テンプレート全文を応答に貼らない。

1. 本手順書と、指定 ID の行を [demo-publication-priorities.md](demo-publication-priorities.md)・[demo-improvements.md](demo-improvements.md)・[課題対応表](demo-problem-solution-experience-map.md) から読む。
2. ローカルのデモ本体パスを特定する（§7）。
3. デモ側に `docs/executive-ux-roadmap.md` が無ければ **Phase UX-0 のみ**（計画書の作成。コード変更なし）。
4. ロードマップがあり、ユーザーがフェーズ番号を指定していれば **その1フェーズだけ** 実装する。
5. 指定が「ブラッシュアップして」だけでフェーズが無い場合は、未完了の最小フェーズを提案して止まる。勝手に全フェーズを走らせない。
6. 画面を変えたらブラウザで代表3手を操作して確認する。スクリーンショット1枚は合格にしない。
7. 全フェーズ完了後にだけ、`ideal_pf` の紹介文・`can` / `planned`・必要ならスクショを同期する。

### 鉄則

1. **1 Phase ずつ。受け入れを満たしてから次へ。**
2. **デフォルト画面に技術用語・設定盤・ROI を出さない。** Experience を本物の業務画面／顧客画面にする。
3. **Experience（前半）と Adoption（後半）を同じフェーズで混ぜない。**
4. **カスタマーサポートの「店舗サイト背景＋右チャット」は、店舗チャット型にだけ使う。** シフト・報告書・記録系にコピーしない。
5. **AI接続は `@axeon/ai-demo-core` 経由を維持する。** Access Mode / Trial は削除せず、初期視野から外す。
6. **本番API・別アプリ分割・スコープ外の新機能を、磨きのついでに足さない。**

## 3. 再利用する骨格（カスタマーサポートから残すもの）

残すのは画面の見た目ではなく、**商談3分の順番**である。

| 順番 | 問い | 成果 |
|------|------|------|
| 0. 3分ストーリー | 決裁者が最後に何を言えるか | 1文のゴールとフェーズ表 |
| 1. 入口のダイエット | 最初の画面で何が邪魔か | 説明・設定・二重CTAを隠す |
| 2. 代表3手 | 価値が伝わる最短操作 | おすすめ3操作 |
| 3. 結果の読みやすさ | 結論と次の1手が一目か | カード／一覧／下書きの先頭を軽くする |
| 4. 導入の後段 | 自社データ・費用・仕組みは後半か | 体験後またはメニュー内 |
| 5. 台本と掲載文 | 画面と紹介が一致するか | デモ側ドキュメント → その後 `ideal_pf` |

カスタマーサポートはチャット特有の作業が多く、UX-0〜8 になった。他デモは **UX-0〜5 で足りることが多い。** 無理に8個に分けない。1フェーズで対象ファイルが膨れるときだけ分割する。

### Dual Lens（時間差）

| 層 | 商談の時間 | 画面 |
|----|------------|------|
| Experience | 前半。利用者になりきる | 代表操作と結果だけ |
| Adoption | 後半。導入を検討する | 自社データ投入、仕組み、ROI、Access Mode |

同時に出さない。出す場所より **「いまの回答／いまの結果の先頭が隠れていないか」** で判断する。

## 4. 各デモに置くロードマップ（Phase 定義）

保存先: `<デモ本体>/docs/executive-ux-roadmap.md`

Phase 0 でこの見出しを埋め、以降はチェックを進める。

### Phase UX-0 — 計画の固定

- **目的:** ゴール1文、代表3手、消すもの、残すもの、やらないこと、受け入れを文書化する。
- **コード変更:** なし。
- **受け入れ:** 決裁者向けの1文と、画面で Yes/No できる受け入れが3〜6個ある。

### Phase UX-1 — Experience のダイエット

- **目的:** 最初の画面から説明文・デモ操作ボタン・二重表示を削る。
- **受け入れ例:** デフォルトに設定・ROI・「最初からやり直す」が露出していない。読むべき説明が1文以下。

### Phase UX-2 — 代表3手の固定

- **目的:** 迷わず価値が伝わる3操作を最前面に出す（カスタマーサポートの「おすすめ3問」に相当）。
- **受け入れ例:** 3手を順に押すだけで一連の結果まで到達する。

### Phase UX-3 — 結果の読みやすさ

- **目的:** 結論と次の1手がファーストビューで読める。詳細は折りたたみまたは下スクロール。
- **受け入れ例:** 新しい結果が出たとき、先頭（結論）が見える。末尾のバナーや ROI に飛ばない。

### Phase UX-4 — Adoption の後段配置

- **目的:** 自社データ、仕組み、費用、API 設定を体験後またはメニューへ移す。
- **受け入れ例:** 前半は設定の話が視界に入らない。後半はワンタップで開ける。`?explain=1` など営業用起動は壊さない。

### Phase UX-5 — 台本・定義・掲載の同期

- **目的:** デモ側の定義書・チェックリスト・3分台本を実装に合わせ、その後 `ideal_pf` の `can` / `planned` / 紹介文 / 必要ならスクショを更新する。
- **受け入れ例:** 営業が台本どおり3分で完走できる。掲載文が今の画面と矛盾しない。

各 Phase に必ず書く項目:

- 目的
- 対象ファイル
- やること（箇条書き）
- 受け入れ条件（画面で判定できる文）
- やらないこと

## 6. フェーズ完了時の「邪魔検査」

実装が受け入れを満たしていても、商談で壊れることが多い。**画面を変えたフェーズの最後に必ず見る。**

- 新しい結果の **先頭** がスレッド／画面の上部に来るか（末尾へ飛ばないか）
- ROI・設定・技術カードが **操作のたびに** 前面へ出てこないか
- デフォルトに Layer / fixture / LLM / APIキー などの語が無いか
- 同じ CTA が2箇所に出ていないか
- スマホで主操作が欠けないか（PC専用の飾りは許容）

## 7. 指定 ID とローカル本体

掲載 ID とソースフォルダの対応。不明なら `ideal_pf/掲載拡充の進め方.md` の表を正とする。

### A：先に磨く（推奨順）

| 指定 ID | テーマ | ローカル本体（目安） | 画面型の目安 |
|---------|--------|----------------------|--------------|
| `construction-record` | 現場写真と報告書 | `construction_demo` | 業務画面（写真→下書き→管理） |
| `customer-support` | 問い合わせ案内 | `customer_support_demo` | 店舗チャット（**完了。掲載同期のみ残る場合あり**） |
| `shift` | シフト作成・欠勤対応 | `shift_demo` | 業務画面 |
| `contractor-matching` | 協力業者比較 | `hookapp_demo` | 業務画面 |
| `field-dandori` | 電気工事の段取り | `denkigenba_dandori_demo` | 業務画面 |
| `sfa-legal` | 士業の相談案件管理 | `demos/showcase/sfa_legal` | 業務画面 |
| `vietnam-haken` | 人材紹介の選考管理 | `demos/showcase/vietnam_haken` | 業務画面 |

主力の確認順（掲載方針と同じ）: **建設 → カスタマーサポート → シフト**。サポート本体の UX は完了済みなので、次の指定は建設かシフトが自然。

### B：代表1シナリオの完走を先に（見た目の刷新は後回し）

不足している「途中で止まる操作」だけを直す。フル UX-0〜5 は、A が終わってからでよい。

優先の目安: `internal-knowledge`、`kaigo-handoff`、その後に製造1件（`manufacturing-compare` または `quality-incident` / `approval-inspection` のいずれか1つ）。

### C / D：この手順では着手しない

統合・補助資料・切り口の再検討。UI 磨きに入れると掲載方針と実装が二重管理になる。ユーザーが明示したときだけ、この手順書ではなく掲載方針の「戻す条件」に従う。

## 8. `ideal_pf` 側の更新（Phase 5 の後半）

デモ本体が固まってから行う。途中フェーズでは紹介文を書き換えない。

1. `src/data.js` の当該 ID: `can` / `planned` / `experienceNote` / `lead` を今の3手に合わせる
2. 必要なら `docs/demo-improvements.md` の「次の改善」と確認日を更新する
3. 画面が大きく変わったときだけスクショを取り直す（途中撮りは捨てる）
4. 課題対応表の「体験」列が代表3手と食い違うときだけ直す

ROI シミュレータへ繋ぐ場合は [roi-simulator-demo-integration.mdc](../../.cursor/rules/roi-simulator-demo-integration.mdc) に従う。チャット本文や結果カードの直下に常時出さない。

## 9. 工数目安

| 種類 | 目安 | 内容 |
|------|------|------|
| A のフル磨き | 半日〜1.5日 | UX-0〜5 |
| B の完走修正 | 数時間 | 止まる1操作の修正＋確認 |
| カスタマーサポート級 | 複数日 | チャット＋埋め込みなど型そのものの刷新。例外 |

並列で複数デモを磨かない。1本の Phase を閉じてから次の ID を指定する。

## 10. やらないこと

- 28件への店舗チャットレイアウトの横展開
- C/D の見た目刷新
- 計画前のコード改修、または計画中の本番機能追加
- 先に `ideal_pf` の紹介文だけを磨く（画面とすぐズレる）
- フェーズ完了を「ビルドが通った」だけで宣言する
- `@axeon/ai-demo-core` の再実装、体験コード取得画面のデモ内複製
