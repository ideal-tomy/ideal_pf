# デモの掲載・統合・作り込み方針（暫定案）

作成日：2026年9月12日

## 1. 判断の前提

28件をすべて同じ重さで掲載する方針から、課題と解決方法を説明でき、その内容をデモで確かめられるテーマに絞る方針へ移すことを提案する。

本書は [課題・解決・体験の対応表](demo-problem-solution-experience-map.md)、[紹介データ](../src/data.js)、[内部改善管理](demo-improvements.md)に基づく企画判断。外部デモの実操作、各デモ本体の実装調査、需要・競合・問い合わせ実績の調査は今回行っていない。したがって「テーマの価値」は市場性の確定評価ではなく、今回のサイトで業務改善を説明する題材としての価値を指す。

**現時点で「テーマと十分なデモが揃っている」と確定できるものはない。** URL応答や画面の存在だけでは判定できないため、以下のAは最初に実操作で確かめる掲載候補とする。固定サンプルでも課題と結果が伝われば掲載価値がある。実AI接続の有無は主な評価軸にしない。

「一覧から外す」は、公開一覧・おすすめからの非表示を指す。ソースやデモ本体の削除は提案しない。既存の共有URLは維持するか統合先を案内する。今回、掲載設定やコードの変更は行っていない。

## 2. 評価軸と仮分類

| 評価するもの | 判断する問い |
|---|---|
| 課題の具体性 | 誰の、どの仕事の、何が困るのかを一文で言えるか |
| 解決の説明力 | 画面を導入すると何が変わるのか、業務の流れで説明できるか |
| 独立掲載の意味 | ほかのテーマと異なる読者・課題・判断材料があるか |
| 体験の対応 | 説明した解決を、入力・確認・結果の流れ、または明確な説明で確かめられるか |
| 現在との差 | 足りないのは公開URLか、操作の仕上げか、シナリオ自体か |

| 区分 | 件数 | 判断と扱い |
|---|---:|---|
| A：先に掲載を整える候補 | 7 | 具体的な課題と代表操作が現行説明にある。実操作確認後に掲載を強める |
| B：テーマを残し、体験を完成させる候補 | 11 | テーマの筋はあるが、実操作の確認不足・未対応操作・公開準備が残る |
| C：独立掲載をやめ、統合・補助資料に回す候補 | 7 | 課題自体には価値があるが、現在の切り分けでは重複や説明の薄さがある |
| D：現在のテーマを保留し、切り口から再検討 | 3 | 題材が広い、または業務改善の説明として弱い。文章を磨く前に対象と結果を絞る |

最初の方向性は「7件の掲載候補を確認し、11件の改善候補を順番に育てる」。28件から機械的に18件へ減らす決定ではない。実操作と対象顧客との適合を見て、分類を更新する。

## 4. 「テーマはあるがデモがない」の扱い

今回の28件はすべて何らかのデモ紹介データがある。「URLがない7件」を「デモが存在しない7件」と数えない。

| 状況 | 該当例 | 先に行うこと |
|---|---|---|
| 既存体験があり、公開が主な不足の可能性 | manufacturing-compare | ローカル体験の再確認と公開準備 |
| 既存実装と体験の範囲が不明 | inspection-record、pharmacy-transfer、property-match | 本体を調べ、新規制作と補修を区別する |
| テーマに対して体験の終点が足りない | quality-incident、approval-inspection、haken-dash | 課題が解決に向かう結果まで、一つの操作の流れを完成させる |
| 切り口から再設計が必要 | expense-optimize、sns-post、assist-reception | 誰が何を判断・完了するかを決めてから開発する |

**完全新規のデモは、現時点では優先しない。** まず既存デモの中で、課題の説明と操作の結果が切れている部分を埋める。

追加を検討するなら、既存テーマを次のように発展させる案がある。以下は現在の実装を確認できていない新規・追加シナリオ。

- 設備点検：異常を記録 → 対応担当者へ引き継ぐ → 対応後に完了を確認。
- 問い合わせ・受付：案内で解決しない質問 → 担当者が受け付ける → 対応状況を確認。
- 介護連携：記録を確認 → 次の役割に必要な情報を渡す → 次の対応を確認。

共通する狙いは、入力や一覧表示から一歩進み、「次の仕事につながる」ところを体験にすること。

## 5. 何から作り込むか

指定したデモ本体の磨きは、[demo-ux-brushup-playbook.md](demo-ux-brushup-playbook.md) に従う（3分体験の固定 → 1フェーズずつ実装 → 最後に紹介文を同期）。

### 第1段階：掲載候補の実操作確認

最初に construction-record、customer-support、shift を確認する。代表入力、結果、初期化・再体験の手順を記録し、説明文と画面が一致したものから主力として整える。新機能を広げる前に、今ある体験の価値を確かめる。

### 第2段階：主力にする2件の不足を埋める

| 順序 | 対象 | 最小限の完成形 | 完了の判断 |
|---|---|---|---|
| 1 | internal-knowledge | 一つの社内資料に対し、代表質問から回答と根拠へ確実に進める | 初めての人が回答と元の根拠を確認できる |
| 2 | kaigo-handoff | メモを整理し、人が確認・修正して記録一覧へ進める | 説明した内容が記録に反映され、固定入力・保存条件も理解できる |

既にこの流れが動けば、大きな改修は不要。確認して不足部分だけを直す。この2件が整えば、建設・問い合わせ・シフト・社内資料・介護という主力5テーマの案ができる。前回おすすめに含まれていた品質トラブルは、体験完成まで主力枠から外す案。

### 第3段階：製造で代表1件を選ぶ

manufacturing-compare をまず確認する。既存の比較体験が明快なら公開を先行する。そうでなければ、具体的な対象顧客に合わせて品質トラブル対応または受入検査を選び、1シナリオを完成させる。3件を同時に広く作り込まない。

### 第4段階：業種別に追加

Aの残る4件を整え、食品・保育・自治体・薬局・不動産は対象顧客との接点と実操作の不足量で着手順を決める。PDF・動画は代表シナリオが固まったものから制作する。

## 6. 実操作後に掲載を決めるチェック

各デモについて、以下を一枚の確認記録に残す。

- 対象者と課題を一文で説明できるか。
- 最初の画面で何をすればよいかわかるか。
- 代表的な入力・選択から結果まで到達できるか。閲覧型なら、説明の結論まで読めるか。
- 結果から「自社の仕事をどう変えるか」がわかるか。
- 固定サンプル、保存範囲、AI接続などの条件が正しく案内されるか。
- 類似テーマより独立掲載する意味があるか。

判定は「掲載」「補修後に掲載」「補助資料へ」「非表示で再企画」の4つ。リンクの応答だけで掲載可にしない。一方、デモに本番システムと同等の永続保存や外部連携まで要求せず、利用条件を明記したうえで代表体験が成立するかを評価する。

## 7. 今回の提案範囲

本書は掲載判断のたたき台。A7件・B11件・C7件・D3件の計28件を整理した。現時点で行うべきことは、C・Dを直ちに物理削除することではなく、主力候補の実操作確認と、独立掲載するテーマの絞り込みである。公開一覧の変更、デモの削除・統合、改修、公開操作は実施していない。
