# PLAN：全詳細ページを現在の建設の型へ統一する

作成日：2026-09-13
状態：計画作成済み／実装未着手

## 1. 目的と対象

現在の建設紹介ページをデザイン・情報構成・操作の基準にし、掲載中の全28詳細ページを同じ型へ統一する。建設1件を共通テンプレートへ移し、他27件へ展開する。将来追加するデモも同じ型を使う。

スマートフォンで「概要をつかむ → 実画面に興味を持つ → 必要な説明を読む → 体験する」という順序を作る。短く見せるために必要な内容を捨てず、同じ説明の繰り返しをまとめる。

対象は `?demo=<id>` で開く全詳細ページ。トップ・一覧・カテゴリ・プロフィール等のページ構成、デモ本体の機能改修、新規公開は今回の展開作業に含めない。ただし、入口と詳細の名称・画像・体験状態の整合、戻る操作は確認する。

このPLANを全詳細展開の正本とする。先行する `featured-demo-design-rollout-plan.md` は5件限定の検討記録とし、対象範囲・冒頭の補足表示などが競合する場合は本PLANを優先する。

## 3. 引き継ぐデザイン仕様

- ダーク背景、丸いアプリアイコン、短い見出し、丸い主ボタン、基本情報3項目を採用。
- 説明欄の最大幅940px、スマホの左右余白22pxを基準とする。
- ギャラリーはスマホでカード幅80%、次のカードが少し見える横スクロール。十分なPC幅では3枚並列。中間幅では可読性を保って横スクロールする。
- 画像の窓は390×600相当。画像高さは最大400 CSS px。上端基準の `object-fit: cover` で切り取り、引き伸ばさない。
- 見出し込みのプレビューカードは通常表示でおおむね600px以内。文字拡大時は内容を切らず高さの増加を許容する。
- 実画面の全体表示より開いたときのバランスを優先する。操作の結果が見えなくなる場合は画像ごとの焦点位置か撮影状態を調整する。
- 色とアイコンは各デモに合わせるが、余白・角丸・文字階層・ボタン・開閉UIは共通化する。
- 自動スライド、新しい装飾アニメーション、画像内スクロール、追加の固定CTAは導入しない。

### 削除済み文言の扱い

`テキスト削除リスト.md` に従い、次の要素を共通テンプレートにも置かない。

1. 冒頭CTA横の「サンプルで体験／写真・APIキーの準備不要」
2. スワイプを促す案内文
3. ギャラリー見出し横の「01 — 03 →」

各カード内の01・02・03は維持する。サンプルやAPIキー等の必要な条件は「体験について」で扱う。スクリーンリーダー向けのスクロール領域名は維持する。

## 4. 全件共通の情報構成

| 順番 | セクション | 内容・編集ルール |
|---|---|---|
| 1 | 戻るヘッダー | 「← 一覧へ」、idealと業種。全件で同じ操作 |

| 3 | 基本情報 | 対象者・体験範囲・確認の前提など3項目。建設の「3ステップ」「人が確認」を一律コピーしない |

| 6 | 見どころと進め方 | プレビューに対応する開閉項目。価値、見るポイント、確認済みの操作方法、必要な場合だけ途中入口 |

「型の統一」は文章量や主張の統一を意味しない。操作デモ・画面紹介・説明ストーリー・紹介のみを、同じ構造の中で正しく表現する。根拠のない削減率・所要時間・評価・実績は追加しない。

### 体験リンクがない場合

- `linkState` と有効なHTTPS URLの両方を満たす場合だけ外部CTAを表示する。
- preparingのページは「紹介のみ／体験版は準備中」を状態として表示し、主ボタンはページ内の「紹介を見る」へ置き換える。空リンクや押せない体験ボタンは作らない。
- 文言は「体験できます」から、実態に応じて「画面を紹介します」「流れを紹介します」へ調整する。
- 保存・送信など動作に制限があるavailableページは、ボタンを「画面を見る」「流れを見る」などに調整し、「体験について」に具体的な範囲を記す。

## 5. 画像の整備方針

実画像登録済み5件は既存画像を確認し、見出しと画面状態が違うものを撮り直す。特に建設の報告書画像は入力の入口を表示しているため、「下書きの確認」を示す画面として適切かを再確認する。

残り23件は次の順に対応する。

1. デモ本体の公開先または対応するローカルプロジェクトを特定する。
2. 掲載する代表画面を原則3つ選び、サンプル・架空データで実画面を取得する。認証・実送信・実データ入力を必要とする場合は取得可能な範囲を記録する。
3. 390×600相当の切り取りで特徴が伝わるか確認する。PC中心の画面は主要パネルを切り出し、全体縮小で文字を潰さない。
4. 実画面を取得できないページは、同じカード枠に業務に即した図解を配置し「画面イメージ」または「流れのイメージ」と表示する。汎用の空欄モックを実画面として扱わない。
5. 図解採用の理由と実画像への差し替え条件を台帳に記録する。画像がなくても旧テンプレートに残さず、共通の型で完成させる。

原則3枚だが、情報が不足する場合は1〜2枚で成立させる。枚数に応じてPCのカラムと領域名を変更し、空カードで水増ししない。画像は先頭を優先表示、残りは遅延読み込み。画像ファイルへの幅・高さ指定は元画像の寸法を使い、CSSで表示窓を制御する。

## 6. 原稿の移し替えとデータ設計

### 既存情報の対応表

| 既存 | 新しい配置 |
|---|---|
| plain / one / lead | 詳細用タイトル・概要へ整理。トップの表現と意味を揃える |
| audience / category | 基本情報と対象者の説明 |
| when | 課題の比較と「どんな業務の悩みに役立つ？」 |
| can | プレビューの見出し、改善後、見どころの本文 |
| shots | プレビュー画像・説明・焦点位置 |
| experienceNote | 「体験について」の常時表示と補足 |
| planned | 現在の未対応機能を利用者向けに説明。内部の実装TODOは管理資料へ |
| relatedIds | 関連するデモ |
| url / linkState | CTAの有無とリンク先 |

全件について、元の説明→移行先→統合・言い換え理由を記録する。短い紹介文から未確認の操作手順や機能を推測して補わない。操作を確認できない場合は、確認できる画面・説明の範囲に留める。

### ファイルの責務（実装案）

- `src/demo-story.js`：共通描画。見出し、CTA、基本情報、プレビュー、比較、details、関連リンクを小さな描画関数に分ける。
- `src/stories/<demo-id>.js`：各ページの編集済み原稿。インデックスでID別に取得する。トップ掲載等の基本情報やURLを重複管理しない。
- `src/data.js`：ID、掲載状態、カテゴリ、トップ・一覧用の情報、URL、関連IDの正本を維持する。
- `src/construction-story.js`：既存の原稿exportと資料書き出しの互換性を保持。共通描画へ渡す変換を設け、建設の長文原稿を重複させない。
- `src/style.css`：建設専用のクラス名を共通名に変更。色と画像の焦点位置はデータで指定し、デモ別のCSS複製を避ける。
- `src/main.js`：全詳細を共通描画へ渡す。建設IDに依存する表示幅、背景inert、タイトル、閉じる処理を全件へ一般化する。
- `docs/detail-rollout-tracker.md`（実装時に作成）：原稿照合、画像の由来、操作確認日、検証、未確認事項をID単位で記録する。

各原稿にはhero、meta、previewMode（連続操作／機能別紹介）、previews、changes、background、details、conditions、closingを持たせる。リンクは確認済みの相対パスまたはURLを明示し、建設の `/photo` 等を他ページへ流用しない。文字列はエスケープし、任意HTMLの埋め込みに依存しない。

## 7. 展開順と完了の区切り

### フェーズ1：共通の型を作る

建設を共通描画に移して視覚差分を確認する。次に問い合わせ1件とpreparingの製造比較1件で、色・文章・画像不足・CTA状態の違いを検証する。この段階で共通構成と例外処理を固める。

完了条件：現行建設のバランスと削除済み文言の状態を維持し、3件が同じ描画関数で成立する。

### フェーズ2：トップ掲載を揃える

シフト・品質・介護を展開する。既存15画像の内容と短い表示窓の対応を確認する。問い合わせを含めたトップ5件を比較し、各デモの個性を色と原稿で表現する。

完了条件：トップ5件すべてで冒頭→画面→説明→体験への流れが揃う。

### フェーズ3：残りのavailable 16件

下の対象一覧のB1・B2・B3の順で、機能が近いグループ単位に原稿整理・画像取得・適用・検証を行う。各グループの完了後に台帳を更新する。画像取得に支障があるものは明示した図解を用い、ページ構成の移行を完了させる。

### フェーズ4：preparingの残り6件

フェーズ1で使った製造比較を含む7件を紹介のみの共通表示へ統一する。URL準備や実AI機能の完成を、このデザイン移行の必須条件にしない。

### フェーズ5：全28件の通し確認と旧実装整理

掲載28IDと共通原稿のIDを照合し、未移行ゼロを確認する。全件の確認が済んでから旧詳細の描画を取り除く。旧CSSはトップや一覧のモック表示と共用していないことを確認してから整理する。

未来の追加デモも同じ描画を使う。原稿不足時も共通テンプレートの最小構成を使い、旧詳細へ戻す分岐は残さない。最小構成では概要・既存の説明・状態・関連のみで成立させ、未確認の比較や手順を自動生成しない。現在の28件は個別の原稿確認を完了させる。

## 9. 操作・表示の統一で確認すること

- 「← 一覧へ」は全件で一覧へ戻す。検索・カテゴリから開いた場合は可能な限りその条件とスクロール位置を復元する。直リンクからは全件一覧へ戻す。
- ブラウザの戻る・進むはURLと表示が一致する。関連デモを連続で開いても戻れ、閉じたときに非表示の要素へフォーカスを戻さない。
- タイトルを各デモ名へ変更し、閉じると元に戻す。背景inertとスクロールロックを全詳細に適用・解除する。
- モーダルのラベル、Escape、Tabの移動範囲、summaryのEnter/Space操作、外部リンクの別タブ案内を確認する。
- preparing、無効ID、非掲載ID、関連ID欠落でも空リンクや例外を発生させない。
- 画像を読み込めない場合はレイアウトを維持し、代替テキストまたは画像未表示の状態を示す。

## 10. 検証と受け入れ条件

- `npm run build`、差分チェック。
- 28IDの原稿網羅、関連IDの妥当性、画像ファイル存在、公開状態とCTAの整合。
- 全28件を390px・1280pxで開き、JSエラー、画像の読み込み、ページ横はみ出し、見出し、CTA、開閉と一覧復帰を確認する。
- 建設、長いタイトル、画像なし、preparing、独立した3機能の代表ページは320・430・700・768pxでも確認。
- 600px程度の低い画面高、200%文字拡大、動きを減らす設定で読めることを代表ページで確認。固定の高さに文章を隠さない。

### 目視確認

全28件のスマホ・PC画像を保存して実際に見る。先頭だけでなく、ギャラリー、詳細を開いた状態、条件、末尾も確認する。

- 開いた直後に何のページか、何を試せるかがわかる。
- プレビュー画像は400px以内、カードは標準文字サイズでおおむね600px以内。スマホで次カードが見える。
- 原稿と実画面が一致し、重要な結果や確認箇所が切り取りで失われていない。
- 削除リストの3要素が復活していない。
- 体験条件と未対応機能が必要な場所に残っている。
- 操作が連続していないものを3ステップの一連の処理と誤認させない。
- 読む必要のない操作説明が常時展開されていない。

実機Safariは利用可能なら確認し、未確認なら検証記録に残す。外部デモ本体の問題は紹介ページの表示不具合と分けて記録し、説明は確認済みの範囲へ合わせる。
