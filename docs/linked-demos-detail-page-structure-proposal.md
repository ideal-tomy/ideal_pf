# 体験デモ付き詳細ページの構成案

作成日：2026-09-19

## 1. 目的と対象

`docs/demo-intro-design.md` と `docs/demo-intro-playbook.md` を紹介アニメーションの設計上の正本とし、`ideal_pf` に掲載されているデモのうち、確認済みの体験 URL がある21件を対象に、詳細ページの情報設計を統一する。

対象は「一覧カードから体験デモへ進める」ことを前提にする。`preparing` の7件（`manufacturing-compare`、`assist-reception`、`inspection-record`、`expense-optimize`、`pharmacy-transfer`、`property-match`、`sns-post`）は今回の対象外とし、URL公開後に同じ型へ追加する。

この文書は実装仕様ではなく、各ページの原稿・画像・紹介アニメーションを作るための構成案である。説明で約束する範囲は、外部デモで確認できた操作と `data.js` の体験条件に合わせる。

## 2. 全ページ共通の構成

詳細ページは、訪問者が「自分の課題に近いか」→「何が変わるか」→「どの画面で確かめられるか」→「実際に試せるか」の順に判断できるようにする。

### 2.1 ページの並び

1. **パンくず・一覧へ戻る**
2. **ヒーロー**：業務テーマ、短い約束、対象者、体験デモへの主CTA
3. **紹介アニメーション**：`見せ切る操作` を字幕・画面・変化で一致させる
4. **どんな業務の悩みに役立つ？**：誰の、どの作業が困っているか
5. **導入すると何が変わる？**：現状と変化を2〜3組で対比
6. **体験の流れ**：入力・確認・判断・次の行動を3〜5段階で図示
7. **画面で見られること**：実画面の画像または、実画面でないことを明記した図解
8. **体験条件**：固定サンプル、AI接続、保存、未対応機能、初期化の扱い
9. **体験デモを試す**：外部 URL のCTA。リンク先でできることを1文で補足
10. **自社への問い**：導入検討時に確認したい業務上の質問
11. **関連デモ**：同じ業種、または同じ業務課題のページ

### 2.2 表示ルール

- 1画面で主役にする情報は1つ。画像・見出し・CTAの優先順位を崩さない。紹介の目的は、視聴者が業務の価値を短時間で理解し、体験デモへ進みたくなること。
- 紹介アニメーションで同時に目立たせる画面は最大2枚。左から右への進行を基本とするが、デモの内容に合わせて、ズーム、焦点移動、積み上げ、切り替え、画面内の状態変化など最も理解しやすく魅力的な演出を選ぶ。
- 実画面とイメージ図を混ぜない。未取得の結果画面は「機能のイメージ」と表示する。
- 体験条件は折りたたみに隠さず、体験CTAの近くに常時確認できる形で置く。
- 画像は入口、代表操作、結果または判断根拠の順に最大3〜4枚。キャプションは画像に実際に写る内容と一致させる。
- 画面幅390px、768px、1280pxで、見出し・CTA・画像・条件が欠けないことを確認する。

### 2.3 演出設計の考え方

現行の紹介アニメーションは、横展開時にそのまま複製するテンプレートではなく、設計と実装のサンプルとして扱う。横展開では、各デモについてマーケターとコンテンツ制作者の視点で「誰に、どんな業務価値を、どの順番で理解してもらうか」を決め、その結果として演出を選ぶ。

左から右への進行は、視線と業務の進行を揃えやすい基本方針である。ただし、デモごとに最適な表現が異なるため、左右の配置を機械的に固定しない。たとえば、単一画面の中で焦点を移す、重要なカードを前面に出す、複数の情報が一つの判断に集約される、入力前後を比較する、といった演出を選べる。

避けるのは「同じ2画面の組み合わせを、今度は右から左へ動かして戻ったように見せる」こと。逆方向が必要な場合は、時間の逆戻りではなく、別の視点・状態・判断結果へ進む意味を画面の変化と字幕で持たせる。

各デモの紹介は、次の順で設計する。

1. 視聴者が自分の業務だと気づく入口を置く。
2. いちばん価値が伝わる操作または判断を一つ決める。
3. その操作の前後で何が変わるかを決める。
4. 変化が最も理解しやすいカメラ・画面構成・字幕を選ぶ。
5. 最後に、体験デモへ進む理由が残るCTAへつなぐ。

### 2.4 紹介アニメーションの設計メモ

各ページの実装前に、次の項目を埋める。型Aは複数人の受け渡し、型Bは一人の単一画面、型Cは同一人物の2画面に限る。

```text
デモ名:
見せ切る操作:
焦点:
利用者の人数:
本物の画面:
つながり: 人から人 / 一人の段階 / 同一人物の2画面
選んだ型: A / B / C
場面表: 順番 / 主役 / 画面で起きること / 字幕
```

## 3. デモ別の構成案

### 3.1 建設・現場

| ID | ページの主題 | 紹介で見せ切る操作 | 型 | 詳細ページの体験の流れ |
|---|---|---|---|---|
| `construction-record` | 現場写真の整理から報告書と確認業務まで | 写真を選ぶ → 工種・場所を確認 → 報告書の下書き → 確認・承認へ渡す | A：リレー型 | 現場の写真選択 → 自動整理 → 報告書下書き → 内勤の確認 → 責任者の承認。差し戻しがある場合は例外として示す |

チャット系は「スマホで聞き、別のPCが答える」ように見せない。質問・回答・根拠を同じ画面の状態変化として見せる。

## 4. CTAと体験条件の書式

### 4.1 主CTA

```text
このデモを試す → [確認済みの外部URL]
この体験で確認できること：入力／選択 → 結果確認 → 次の判断（実装範囲に合わせる）
```

URLが空のデモはこの案の対象外。外部デモが一部機能のみの場合は「画面紹介」「固定サンプル」「保存なし」などをCTA直下に出す。

### 4.2 体験条件の必須項目

- サンプルデータか、利用者が入力できるか
- 固定回答か、実AI・外部連携があるか
- 保存・提出・送信が実際に行われるか
- 再読み込み・リセット・初期状態の戻し方
- 未対応または確認中の機能
- 外部デモで個人情報・実案件を入力しない注意

## 5. 実装PLAN（サンプル実装からの横展開）

### Phase 1：デモごとの企画

- 対象者、業務上の困りごと、導入後に伝えたい変化を1文で定義する。
- 視聴者が最初の5〜10秒で理解すべき価値を決める。
- 代表操作・判断・結果を一つ選び、紹介の到達点にする。
- 画面、素材、サンプルデータを確認し、実在しない担当者や処理を追加しない。

### Phase 2：演出コンテ

- 入口、価値が最大化する場面、結果、体験CTAの4ブロックで短い絵コンテを作る。
- 各ブロックに主役画面、焦点、画面の変化、字幕、次へ進む理由を記載する。
- 左から右を基本にしつつ、デモに合う演出を比較し、同じ画面ペアの単純な往復は採用しない。
- 紹介アニメーションは説明の代替ではなく、体験へ進む動機を作るものとして評価する。

### Phase 3：実装

- 現行の紹介アニメーション実装をエンジンのサンプルとして参照する。
- 再生・停止・再開・周回・モーション低減・レスポンシブ対応は共通化する。
- story、画面部品、字幕、焦点移動はデモごとに書き換える。
- 再生中にAPI・保存・送信を実行しない。

### Phase 4：マーケティング検証

- 初見の人が、対象業務・変化・次に試すことを説明できるか確認する。
- 動きが目を引くだけで業務価値が伝わらない場合は、演出より字幕・画面の順序を修正する。
- 体験デモへ進むCTAが自然に見えるか、視聴後の導線を確認する。
- 390px / 768px / 1280pxで、主役・字幕・CTAが欠けないことを確認する。

### Phase 5：横展開

21件を一括コピーせず、各デモの企画・絵コンテ・実装・検証を1件ずつ完了させる。完成したデモの設計メモと実装を次のデモの参考にするが、画面配置、秒数、場面数、字幕はコピーしない。

## 6. 制作・検証の順番

1. `data.js` のURL、体験条件、掲載文を確認する。
2. 対象デモで代表操作を1回通し、詳細ページの終点を決める。
3. デモ別の紹介設計メモ（見せ切る操作・焦点・型・場面表）を書く。
4. 入口・代表操作・結果または根拠の画像を取得し、実画面と図解を分類する。
5. 共通テンプレートへ原稿・画像・条件・CTAを登録する。
6. 390px / 768px / 1280pxで表示、画像、開閉、キーボード操作、一覧復帰、外部リンクを確認する。
7. 紹介アニメーションは停止・再開・周回・モーション低減を確認し、API・保存・送信が再生中に走らないことを確認する。

完了条件は、21ページすべてが共通構成を使い、説明した操作と体験デモの実際の到達点が一致し、条件と未確認事項がCTAの近くで読める状態とする。
